# API Contract — Game Service Plane

**Status:** implemented prototype contract for runtime v0.6.  
**Source of truth:** `services/game-api/internal/httpapi/api.go`.

This document describes the HTTP surface that exists today. It is not a promise that the API is stable for public third-party clients.

## Authentication model

### Player session
Player endpoints use:

```http
Authorization: Bearer <session_token>
```

Session tokens are generated by the service and persisted only as hashes.

### Resume key
`POST /v1/sessions/bootstrap` accepts an optional `resume_key`. A missing key creates a new durable identity and returns a new resume key. Resume keys must be treated as credentials.

### Gameplay ticket
A logged-in client may request a one-time short-lived gameplay ticket. The ticket is redeemed by an authorized gameplay server using:

```http
X-Game-Server-Key: <server-only-secret>
```

The current ticket TTL is 60 seconds.

## Endpoints

### GET /healthz

Checks service-store dependency health.

Success:

```json
{"status":"ok"}
```

A failed dependency returns HTTP 503.

### POST /v1/sessions/bootstrap

Request:

```json
{"resume_key":""}
```

Response HTTP 201:

```json
{
  "session_token":"...",
  "resume_key":"...",
  "snapshot":{}
}
```

`resume_key` is returned only when newly generated.

### GET /v1/state

Requires Bearer session. Returns the current authoritative snapshot.

### POST /v1/game-tickets

Requires Bearer session.

Response HTTP 201:

```json
{
  "ticket":"...",
  "expires_in_seconds":60
}
```

### POST /v1/internal/game-tickets/redeem

Requires `X-Game-Server-Key`.

Request:

```json
{"ticket":"..."}
```

Success returns the authoritative player snapshot. Tickets are single-use.

### POST /v1/quests/{questID}/complete

Requires Bearer session.

Request:

```json
{"operation_id":"client-generated-stable-operation-id"}
```

Quest IDs must match the canonical MQ sequence. Durable mutation operation IDs provide idempotency/replay protection.

### POST /v1/vehicles/{vehicleID}/builds

Requires Bearer session.

Request:

```json
{
  "expected_revision":1,
  "part_ids":["part_id_1","part_id_2"],
  "operation_id":"stable-operation-id"
}
```

The mutation validates:
- ownership,
- expected active revision,
- canonical part IDs,
- blueprint requirements,
- inventory availability,
- operation-ID binding.

## Error model

Errors are JSON:

```json
{"error":"error_code"}
```

Current codes include:
- `invalid_json`
- `missing_session`
- `unauthorized_session`
- `unauthorized_game_server`
- `invalid_game_ticket`
- `invalid_quest_id`
- `invalid_operation`
- `invalid_build_mutation`
- `not_found`
- `state_conflict`
- `quest_prerequisite_incomplete`
- `operation_id_conflict`
- `insufficient_inventory`
- `blueprint_required`
- `invalid_domain_input`
- `dependency_unavailable`
- `internal_error`

## Security constraints

- Do not expose `X-Game-Server-Key` to packaged clients.
- Plain HTTP is local-development only.
- Do not log raw session tokens, resume keys or gameplay tickets.
- All future public mutations should preserve explicit actor/context and idempotency semantics.
- API version changes that break durable clients require explicit migration/versioning.
